## Why this can't be automated

Two paths were attempted on 2026-08-17. Both are closed, so applying this batch is a manual job.

**Editing the existing Routines — refused.** `update_trigger` rejects every field, prompt and
settings alike:

> `update_trigger`: this routine was created via "http_api", not by an agent. Agents can only
> update routines they created (via create_trigger). A routine's own session may still disable
> itself (enabled=false only).

This covers renaming and disabling too, not just the prompt — so an agent cannot retire these
Routines, only their own firing sessions can.

**Recreating them as new Routines — possible but useless.** `create_trigger` succeeds, but the
Routine it produces cannot reach Gmail:

> warning: this trigger stores no MCP connectors, so the sessions it fires will run without
> connector (`mcp__<server>__*`) tools. […] If the routine needs connectors, create it from a
> session that holds them, or ask the user to create it from the claude.ai routines UI.

Passing `connectors` explicitly is also unavailable: *"the connectors parameter is not available
for this organization."* A Routine with no Gmail, Calendar, Calendly or HubSpot would hit its own
first instruction — *"if any of the required connectors doesnt work after retrying, stop"* — and
stop, every run.

A v2 deep-sent-scan Routine (`trig_01W1SwwgucqscFzv1DjAWktE`) was created during this attempt and
**deleted** once the connector warning showed it would fire broken; it never ran. The Routine list
is back to its original five and the three live email Routines were never modified. Two further
divergences argue against the recreate path even if connectors were fixed: an agent-created Routine
cannot set `model` at creation time, and its `session_context.allowed_tools` comes out as
`preset:default` rather than the explicit tool list the originals carry.

**Net:** these Routines can only be edited where they were created — the claude.ai Routines UI.
